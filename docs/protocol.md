# Marathon Turn Protocol — v0

Wire specification for the delta-encoded turn payload. Implemented in `src/marathon/protocol.py` and `src/marathon/diff.py`.

## Content addressing

All state is addressed as `sha256:<64 hex chars>` over its canonical bytes. Canonical bytes are produced by `canonical.canonical_bytes`: JSON with sorted keys, separators `(",", ":")`, `ensure_ascii=False`, UTF-8 encoded, NaN/Infinity forbidden. Histories serialize via `canonical.serialize_history` as canonical JSON Lines, which guarantees the append-only property: `serialize_history(h[:k])` is a byte-prefix of `serialize_history(h[:k+1])`.

## Turn payload

```json
{
  "v": 0,
  "baseline_hash": "sha256:…" | null,
  "target_hash": "sha256:…",
  "delta": { "v": 0, "block_size": 64, "ops": [["c", offset, length], ["i", "<base64>"]] },
  "new_input": "…"
}
```

`baseline_hash` is `null` on the first turn of a session, meaning the empty baseline (zero bytes). `target_hash` is the content address of the state the client is asserting after this turn. `delta` transforms the baseline bytes into the target bytes. `new_input` is the fresh user input for this turn.

## Delta ops

`["c", offset, length]` copies `length` bytes from the baseline starting at `offset`. `["i", "<base64>"]` inserts literal bytes. Applying the ops in order concatenates their outputs to produce the target. Copies out of the baseline's range are a hard error. `block_size` records the granularity used by the matcher; it is informational for the applier (application is fully determined by the ops) but required for reproducing the delta.

## Reuse plan

The delta carries enough information to tell the KV layer what to do, not just what changed. `reuse_plan.plan(old_state, new_state, tokenize, head_tokens=…)` classifies a transition and emits a **list of reusable segments**. Position-shifted KV reuse — keep whatever runs of history survived, recompute only the rewritten entries, and re-rotate each surviving run's keys by *its own* shift — is exact for position but approximate for attention: a reused run's KV attended to the *old* text before it. Measurement (findings, 2026-08-18) puts the boundary at the kind of span edited, not at whether later text depends on it: fact-carrying edits survive plain reuse, because the query attends to the rewritten span directly and the reused text only carries the pointer, while edits inside a **governing** span — system prompt, standing instructions, persona, output-format or language directives, tool policy — moved the first generated token by 30x the KL of every other case. A message is governing when it serializes `"governing": true`; the `system` role gets it by default, and the key is written only when true, so canonical bytes of sessions that never set it are unchanged.

Matching is done on canonical JSONL lines — the ledger's own unit — so a segment is always a whole run of entries and never needs snapping to a token boundary. Where several old entries are byte-identical (every bare `"ok"` acknowledgement is the same line), the *nearest* one is matched, not the first: byte identity is not context identity, and a reused entry's KV encodes whatever preceded it. It is order-agnostic: an entry that *moved* is still the same entry, so a segment's source range may run backwards relative to its neighbours', and its `delta` may be negative. `tokenize` maps one line to the token ids it contributes to the prompt, and `head_tokens` is the length of anything the prompt puts before the first line, so the coordinates are the serving layer's.

- `segments` — the reused runs in destination order. Each is a `Segment(src_start, src_end, dst_start)` with `delta = dst_start - src_start` and `length`. Everything they do not cover is recomputed.
- `moved` — parallel to `segments`: whether that run *relocated* (its entries' index in the history changed) rather than merely shifting because something before it changed length. Measurement (findings, 2026-08-19) is that a shift is safe to re-rotate and a relocation is not — a block that moved 10k positions has KV summarising a completely different prefix, which re-rotation cannot repair and a leading-chunk recompute does not fix — so relocated runs are recomputed by default.
- `total` — length of the new sequence in the same token coordinates.
- `policy` — `reuse` (stitch and go), `repair` (stitch, but natively recompute the first `repair_first` tokens of every non-leading segment so they attend to the new text before them), `full` (nothing survived; recompute).
- `repair_first` — leading tokens of each non-leading segment to recompute; 0 unless `policy` is `repair`, default 256.
- `reason` — why this policy was chosen.
- `p`, `e_start`/`e_end`, `delta`, `s_start`/`s_end` — the earlier single-span vocabulary, kept as derived properties: the leading prefix, the first recomputed span, and the last reused segment.

`plan(...).to_kv_transfer_params()` emits a **list** of `{"dst_start", "dst_end", "delta"}`, one per reused segment past the leading prefix, in destination order — `dst_start` already past the repaired head. Relocated segments are omitted; `to_kv_transfer_params(reuse_moved=True)` includes them, which is measured-unsafe and exists only to re-measure it. The leading prefix is omitted because the serving layer's own prefix cache already holds it; every later segment needs the connector even at `delta == 0`, since a recomputed span before it has already broken the prefix. An empty list means there is nothing for the connector to do. Block alignment stays with the caller, since vLLM only counts matched tokens in whole blocks — and because that API can only express matched tokens as a *prefix*, `k` segments are handed over as `k + 1` requests (`local_probe._phases`), each stopping on the block boundary where the next segment begins.

## Connector

`marathon.vllm_shift_connector.MarathonShiftConnector` is the serving-side consumer of a reuse plan inside vLLM 0.27. Every request carries `{"session": "<id>", "load": {...}, "save": true}` in `kv_transfer_params`; `marathon.shift_store` holds the bookkeeping, which is what the CPU tests cover.

What is safe now. The KV store is **keyed by session id**, one position-indexed buffer per session per layer, so two sessions can never read each other's KV; a request with no session id is pass-through, behaving exactly as if no connector were configured. **One writer per session** is enforced, not assumed: if a second in-flight request claims a session the table refuses it, the request is served with no reuse at all, and a load therefore can never overlap an in-flight save on the same session. **Saves are per scheduler step** — only the positions the request actually computed (`num_computed_tokens` onward, gathered after each layer is written), so chunked and continued prefills are recorded correctly, and a save at a lower `dst_start` truncates the positions above it, which is what an edit means. **Memory is bounded**: a total budget in tokens (`MARATHON_STORE_TOKENS`, default 32768; 164 KB/token on Qwen3-14B) with LRU eviction of whole sessions. Because eviction happens on the worker, the scheduler side mirrors the same bookkeeping without tensors and **declines** a load whose source positions were evicted or truncated — a miss costs a recompute, never a wrong answer. `stats()` reports tokens per session, hits, misses, loads, saves and evictions.

What is still not safe, honestly. Tensor parallelism is untested (each worker would keep its own store, and nothing coordinates them). Preemption is untested: a request preempted and recomputed mid-flight keeps its store positions, and nothing has measured whether the scheduler's re-issue lands on the same coordinates. Chunked prefill *interleaved with* a load on the same request is untested — the probe always hands a load to a request whose local prefix hit already ends at `dst_start`. Reuse is still whole-block only, so a ragged head or tail of a reused run is recomputed. And the store is GPU-resident with no CPU/disk tier, so the budget is a hard ceiling rather than a paging policy.

## Server

`marathon.server.MarathonServer` is the whole pipeline behind one method, `turn(session_id, payload) -> dict`, and `marathon.client` is the other half. The server owns a `BaselineStore`, the last verified state per session, and a vLLM engine with the shift connector attached.

A turn runs in five steps. **Verify**: `resolve_turn` resolves the baseline, applies the delta, and rejects the payload unless `sha256(result) == target_hash` — nothing downstream ever sees an unverified reconstruction, and a rejected payload never reaches the engine. **Render**: the verified state is decoded to messages and pushed through the model's own chat template by `ChatTokenizer`, which recovers the token ids *each message contributes* so the plan's coordinates are the serving layer's. **Plan**: `reuse_plan.plan` classifies the transition from this session's previous verified state. **Drive**: `reuse_plan.phases` turns the reused segments into the k+1 requests the connector API needs, and all of them carry this session's key in `kv_transfer_params`. **Report**: the reply plus `prefill_s`, `prompt_tokens`, `reused_tokens`, `segments`, `policy`, `reason`, `phases`, `wire_bytes`, `state_bytes`.

Chat templates are not append-only as written, which would silently corrupt every coordinate after the first assistant turn. Qwen3 renders a *trailing* assistant message with an empty `<think>` block and drops it as soon as another message follows, so `ChatTokenizer` renders each prefix with a throwaway sentinel message appended: every real message is then in a non-final position and the renders genuinely nest. The sentinel's rendered block is derived from the template (render it twice, subtract one render) rather than hardcoded, the prefix property is checked per message rather than trusted, and the ids handed to the engine are always a single encode of the full prompt — the pieces supply only the lengths.

Sessions are isolated end to end: previous state, per-line token cache and connector store key are all keyed by session id. The store is a flat position-indexed buffer, so it is only meaningful in *one* set of coordinates at a time — an append-only turn extends it, but an edit turn moves everything after the edit and would leave it describing a layout that no longer exists. So the edit turn's final request saves with `"full"`: the connector re-gathers the whole prompt out of the paged KV cache — where the loaded span, the prefix-cache hits and the freshly computed tokens are all resident by then — and writes it back at its *new* positions. `reserve` treats a save at position 0 as a truncating rewrite, so the store comes back contiguous in the new coordinates and the session is append-only again. That is what makes a session's second, third and Nth edit cost the same as its first (measured, findings 2026-08-19). All of a step's loads are issued in `start_load_kv` before any `save_kv_layer` runs, so the re-read can never race the load that fed it.

**Staleness ceiling.** Reused KV is stale by construction: it attended to the text that preceded it when it was computed, and an edit turn re-saves the span it just loaded, so nothing ever recomputes it. For Phase 1's pattern — isolated edits separated by ordinary turns — that is harmless and measured so. For a *paged* session it is a ratchet: demoting the oldest message is a front-of-view edit on every single turn, so by turn N the reused span has accumulated N demotions of drift against text that is no longer there, and the model starts answering from the freshly computed stub tokens instead of the reused content. `max_stale` bounds it by spending one honest recompute after that many *consecutive* reused edit turns. An append-only turn needs no reuse and resets the counter, so the default of 1 costs Phase 1 nothing while holding a paged session at full quality (measured, findings 2026-08-19: fact exact-match 0.20 unbounded, 0.50 at 4, 1.000 at 1, against a no-reuse control of 1.000).

**Churn ceiling (alternative).** Counting *turns* treats every reused edit turn as equally damaging, which it is not: what degrades reused KV is how much of the context it attended to has since been rewritten, and a run of tiny edits is not a run of demotions. `max_churn` bounds that quantity instead. `shift_store.churn_tokens` reads a turn's reuse plan and returns the tokens lying in front of the deepest reused segment that the plan does *not* reuse — exactly the text rewritten ahead of the carried-over KV, which is the demoted message minus its stub on a paged turn and zero on an append-only turn. The server accumulates that across consecutive reused turns and refreshes once `accumulated / span_length` crosses the threshold, resetting the accumulator. When `max_churn` is set the turn counter is not consulted at all. Both are per session, and both are reported per turn (`stale`, `churn`, `refreshed`).

**A shift is not a relocation, and the test is ordering.** A run of reused entries is refused only when its content moved *past* other content; a run that merely changed index because something earlier changed length is a shift, reused with its own delta. Read in destination order, the matched source indices are strictly increasing exactly when nothing was reordered, and a deletion or insertion earlier in the history shifts every later index by a constant without disturbing that. The criterion used to be "this entry's index changed", which is true of every entry after a deleted one — so a cold-tier *eviction* (dropping a stub line from the view is a pure line deletion) was classified as 14 relocated entries and reused nothing at all. Measured 2026-08-19 over four 70-turn paged sessions: at an 8192-token window eviction never fires and the rule costs nothing, but at 4096 it discarded 43% of the turns that can reuse and at 2048, 84%. When the order genuinely is disturbed the old, stricter rule still applies, so a real reorder is no less conservative than before.

**Replay turns do not move either clock.** `turn(..., generate=False)` runs everything but the engine call, so it saves no KV and reuses none; advancing the staleness counter or the churn accumulator there would let a replayed history force spurious refreshes on the real turns that follow it. Both are left untouched on a non-generating turn.

The HTTP front door is `POST /v1/turn` with `{"session": "<id>", "payload": {...}}`, served by stdlib `http.server` — the offline vLLM engine is blocking and single-tenant, so an async framework would add an event loop to block and nothing else. A rejected reconstruction answers `409` with `{"error": "IntegrityError" | "UnknownBaselineError", ...}`; a malformed request answers `400`. Neither kills the server.

The client (`marathon.client.Client`) holds the full logical history and ships only deltas. Assistant replies are appended locally *without* a protocol round trip — they are not a state the server acknowledged, so they must not advance the baseline; they simply join the next turn's delta. `local(server)` and `http(url)` are the two transports, same one-function interface. `Client.edit(session_id, index, content)` rewrites an earlier message; it takes effect on the next turn.


## Cold tier

`marathon.cold.ColdTier` is the paging policy over a session's history, and it is the whole of Phase 2's client-side machinery. The ledger already holds every message content-addressed, so demoting one costs nothing and loses nothing: the bytes stay in the ledger, and only the *active view* -- the thing that actually gets tokenized and prefilled -- swaps the message's text for a stub line, `[cold #12 3f9a1c04: Entry 12. A follow-up ticket tracks the remaining cleanup in the]`. The hash is the first 8 hex of `sha256` over the message's canonical bytes, so a stub is the same content address the ledger would give it: a verifiable pointer, never a paraphrase, and cheap to promote back exactly.

The view is a pure function of `(messages, demoted, evicted)` and the stub a pure function of `(index, canonical bytes)`, so a paged session serializes byte-identically on any replica and hashes, replay and the reuse plan stay exact. Role and the `governing` flag are preserved -- only content changes -- which means **a demotion is an ordinary shrink edit of the view and a promotion an ordinary grow edit**. That is deliberate: it is exactly the shape `reuse_plan` already prices cheaply, so the cold tier needs no new serving path and inherits position-shifted KV reuse for free.

Two things are never demoted: **governing** spans (the system prompt and anything flagged `governing`) and the **last K messages** (the working set, `keep_last`, default 6). Demotion is oldest-first: deep history is the cheapest thing to lose and the stub keeps a pointer to it, so a wrong choice is recoverable rather than destructive.

Stubs alone do not bound anything. A stub is ~20x smaller than the message it replaces, but 20x smaller is still O(n), and on a long enough session the stubs by themselves fill the window. So when there is nothing left to demote and the budget is still blown, the oldest stubs are **evicted** from the view outright. Nothing is lost: the bytes are in the ledger and the retriever searches every demoted message, evicted or not, so an evicted message is exactly as recallable as a stubbed one -- it just stops costing tokens. This is the step that makes the window genuinely bounded rather than merely smaller, and it is what the bounded-window tests assert. It has one cost, and it is a real one: an eviction *deletes* a line, which relocates every line after it, and `reuse_plan` recomputes relocated blocks by design rather than transplanting KV that summarised a different prefix. A demotion-only turn is a pure shift and reuses; a turn that also evicts does not.

Recall-on-miss has two triggers, and every promotion and demotion is logged with a reason because a wrong demotion degrades the model's ground truth silently. **Exact**: the incoming turn's delta touches a demoted message -- an edit landed inside text the model can no longer see -- detected by comparing canonical bytes per line, the same comparison the delta engine makes, not guessed. **Query**: the new user turn is embedded together with the demoted messages by a small local encoder (mean-pooled `all-MiniLM-L6-v2` through plain `transformers`; `sentence-transformers` is one dependency for one line of pooling), and the top-k above a cosine threshold come back, k<=2 per turn. Exact wins over query: a message the delta touched is promoted regardless of similarity. Promoted messages are pinned for that turn, so if the window then overflows the policy demotes *something else* rather than undoing the recall.

The retriever runs on **CPU** by default, and that is not an oversight. It shares a process with the serving engine, vLLM is configured to take ~93% of the card, and a second CUDA context allocating into what is left crashes the run with `cudaErrorUnknown` (measured 2026-08-19). MiniLM-L6 is 22M parameters and the policy embeds a handful of messages per turn, so the GPU buys nothing here and costs a serving outage.

`MarathonServer(active_window=N)` (CLI `--active-window N`, with `--no-recall` and `--embed-model`) wires it in. The tier pages the *verified* history before anything is tokenized, and the view -- not the raw state -- is what gets rendered, planned against the previous turn's view, and prefilled, so promotions and demotions flow through the same verified-state + reuse-plan + shift-connector path as any other edit. Paging is per session, created on first use. The per-turn report gains `active_tokens`, `cold_count`, `cold_before`, and `promotions` / `demotions` with their reasons.

One sizing constraint worth writing down, because it fails loudly and confusingly: the connector's shift store is carved out of the same GPU budget *before* vLLM sizes its own KV cache. On Qwen3-14B at 164 KB/token, a 64k-token store is 10.7 GB, and at `gpu_memory_utilization=0.85` that leaves vLLM **negative** KV cache and the engine refuses to start. The eval runs a 24k store (~4 GB) at 0.93.

## Server obligations

On receipt, the server resolves `baseline_hash` in its content-addressed store — an unknown hash is `UnknownBaselineError`, and the correct recovery is to request a full snapshot, never to guess. It applies the delta and verifies `sha256(result) == target_hash`; a mismatch is `IntegrityError` and the payload must be rejected — reconstruction is proven, never assumed. Only a verified target is promoted into the store as the next baseline.

## Invariants

Idempotence: replaying a payload against the same baseline yields the same target and the same store state. Determinism: two servers with the same store and payload reach byte-identical states. Concurrency: v0 assumes a single writer per session; the ledger's chain hashes make forks detectable but v0 does not resolve them.

## Future versions

v1 candidates, in rough priority order: signed payloads (snapshot signatures over `target_hash`), compression of insert data (zstd) negotiated per session, chunked baselines for very large states (Merkle segmentation so partial invalidation doesn't rehash everything), and an explicit full-snapshot op for baseline recovery.
